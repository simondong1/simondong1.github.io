From WGMMA to TMEM Hopper-to-Blackwell MMA evolution

Hopper made matrix multiplication asynchronous, but its result still occupied thread registers. Blackwell adds a separate 256 KB memory to each SM and moves the accumulator there.

Simon Dong•September 2026•GPU Architecture

The important Blackwell change is not simply “a faster matrix instruction.” It is a new home for the result. Hopper's Tensor Cores write every MMA accumulator into the register file. Blackwell's Tensor Cores write it into Tensor Memory, a new on-chip SRAM attached to the Tensor Core path.

Where this mechanism is used

Datacenter Blackwell kernels such as FlashAttention-4 and SM100 CUTLASS GEMMs use tcgen05.mma and TMEM. Their Hopper predecessors use wgmma.mma_async. For the attention algorithm itself, start with How Flash Attention Speeds Up; this post focuses only on the hardware handoff underneath it.

1.The one-line evolution

Ampere · SM80mma.sync32 threads
inputs and output in registers
Hopper · SM90wgmma.mma_async128 threads

Blackwell · SM100tcgen05.mmaone issuing thread
SMEM/TMEM inputs, TMEM output

Hopper removed most operand staging from registers. A Tensor Memory Accelerator (TMA) copies tiles from HBM into shared memory, and WGMMA reads them there. But the accumulator—the running matrix result—still lands in registers distributed across 128 threads.

Blackwell finishes that separation. The Tensor Core reads its operands from shared memory or TMEM and updates an accumulator in TMEM. The CUDA threads no longer have to own the matrix while the multiplication is running.

TMEM is not TMA

TMA is Hopper's asynchronous copy engine: HBM ↔ shared memory. TMEM is Blackwell's 256 KB accumulator SRAM. B200 has both.

2.Read an MMA shape

Before following the memory, read one Hopper instruction:

One BF16 Hopper WGMMA

wgmma.mma_async.m64n128k16.f32.bf16.bf16

\[ D_{64\times128}\mathrel{+}= A_{64\times16}B_{16\times128} \]
64M: output rows
128N: output columns
16K: reduction depth per issue

The instruction produces—or updates—the entire 64×128 output tile. The 16 is not an output dimension. It says each issue contributes 16 terms to every dot product.

If the head dimension is 256, the kernel issues the instruction \(256/16=16\) times. Every issue consumes the next 16-wide slices of A and B and accumulates into the same 64×128 D tile.

3.Hopper's exact data path

What are we computing? This baseline is one ordinary matrix multiplication, not attention yet. It shows where A, B, and D live during a WGMMA.

1 · Load
TMA: A and B move from HBM → shared memory
2 · Describe
two 64-bit descriptors tell WGMMA each SMEM tile's address and layout
3 · Issue
all 128 threads in one warpgroup execute wgmma.mma_async
4 · Read
A comes from SMEM or registers; B must come from SMEM
5 · Accumulate
D is distributed across the 128 threads' private registers

For FP32 accumulation, a 64×128 D tile contains 8,192 values:

\[ \frac{64\times128\text{ FP32 values}}{128\text{ threads}} =64\text{ registers per thread}. \]

Logically D is one matrix. Physically each thread owns 64 scattered elements. The complete tile exists only when the 128 register fragments are considered together.

4.The register-pressure problem

Now use the real FlashAttention-3 forward tile. One Hopper consumer warpgroup handles 64 query rows and 128 key rows at a time, with head dimension 256:

\[ S=QK^\top,\qquad P=\operatorname{softmax}(S),\qquad O\mathrel{+}=PV. \]
The two matrix multiplies, with dimensions

Q [64×256]  @  Kᵀ [256×128]  =  S [64×128]

P [64×128]  @  V [128×256]  =  O [64×256]

Here S is a 64×128 score tile, P is the same tile after softmax, and O is the 64×256 output accumulator. “RF” means the SM's register file: 64K 32-bit registers divided among resident threads.

Per-thread payload for Q-block 64, K-block 128, head dimension 256. BF16 values pack two per 32-bit register.

The important correction: Hopper does not have to copy P to SMEM

WGMMA has two forms. SS reads A and B from shared memory. RS reads A from registers and B from shared memory. FlashAttention-3 uses the RS form for \(PV\): softmax produces P in registers, and the next WGMMA consumes P directly as operand A. V remains in shared memory as operand B.

No mandatory P → SMEM round-trip

The optimized Hopper path is S in registers → softmax in registers → P remains in registers → RS-WGMMA reads P. Earlier descriptions that always send P to shared memory are reference implementations, not the optimized FA3 mechanism.

The problem is simultaneous ownership. While RS-WGMMA reads P, its O accumulator must also remain in registers. For this 256-wide head, that is approximately \(32+128=160\) payload registers per thread. The two-stage FA3 pipeline also keeps the next 64×128 FP32 score tile, \(S_{\text{next}}\), ready while the current \(PV\) runs—another 64 registers:

\[ P\ (32)+O\ (128)+S_{\text{next}}\ (64)=224 \quad\text{registers per thread, before overhead.} \]

Only 31 registers remain below the architectural 255-register limit for row maxima, sums, scale factors, pointers, descriptors, predicates, and temporary values. Larger tiles or deeper pipelines collide with that ceiling. The FA3 paper explicitly calls out the extra \(S_{\text{next}}\) buffer as the cost that limits pipeline depth.

Hopper works around this rather than simply “spilling”: use a smaller 64×128 score tile, carefully overlap only selected stages, and call setmaxnreg so TMA producer warps surrender registers to the MMA/softmax consumer warpgroup. Good kernels avoid local-memory spills, but the register budget still constrains their schedule.

5.Blackwell's TMEM path

Datacenter Blackwell adds 256 KB of physical SRAM to each SM. It is separate from the existing 256 KB register file and the L1/shared-memory pool. NVIDIA calls it Tensor Memory.

TMEM organization per SM
\[ 128\text{ lanes}\times512\text{ columns}\times4\text{ bytes} =256\text{ KB} \]

software-managed · allocated in columns · accessible only through tcgen05 instructions

Blackwell's replacement for WGMMA is tcgen05.mma, also called UMMA in CUTLASS. Its operand contract is:

TileHopper WGMMABlackwell tcgen05.mma
Aregisters or SMEMTMEM or SMEM
BSMEMSMEM
C / D accumulatorregistersTMEM
Issuer128-thread warpgroupone thread for a CTA or CTA pair
Largest BF16 1-CTA atom64×256×16128×256×16

The Tensor Core writes D directly into TMEM. No CUDA thread owns a D fragment during the MMA. Later, a warp explicitly uses tcgen05.ld to bring a needed slice into registers for ordinary arithmetic or the final store.

This is real new silicon, not a renamed part of shared memory. Ordinary instructions such as ld.shared, ldmatrix, and cp.async cannot address TMEM. Kernels allocate columns with tcgen05.alloc, use them, and release them with tcgen05.dealloc.

Blackwell does not eliminate register use. Softmax is ordinary scalar/vector arithmetic, so FA4 loads one 128-element score row from TMEM into each participating thread's registers. It computes the maximum, exponentials, and row sum there.

The difference is lifetime. FA4 writes P back to TMEM in stages, then the \(PV\) MMA reads P from TMEM while O accumulates in TMEM. The 128×128 S tile and the O tile do not occupy every softmax thread's private register budget for the whole pipeline.

TMEM moves the bottleneck; it does not remove all movement

tcgen05.ld and tcgen05.st still move softmax rows between TMEM and registers. On B200 the exponential unit can become slower than the enlarged MMA path, which is why FA4 also changes softmax scheduling and partially emulates exponentials.

7.How many threads are on one SM?

Both H100 (SM90) and B200 (SM100) can hold at most 64 resident warps = 2,048 resident threads per SM. This is a capacity limit, not the number of threads that execute one matrix instruction.

LevelHopper H100Blackwell B200
Warp32 threads32 threads
MMA issue group4 warps = 128 threads1 thread issues for a CTA / CTA pair
Maximum resident64 warps = 2,048 threads / SM64 warps = 2,048 threads / SM
Register file65,536 × 32-bit registers / SM65,536 × 32-bit registers / SM
Per-thread limit255 registers255 registers
New Tensor Memorynone256 KB / SM

A kernel often keeps far fewer than 2,048 threads resident because registers and shared memory run out first. For example, 256 threads at 240 registers each consume 61,440 of the SM's 65,536 registers. There is no room for another similarly sized block even though 1,792 theoretical thread slots remain.

\[ \text{resident threads from registers} \leq \left\lfloor\frac{65{,}536}{\text{registers per thread}}\right\rfloor, \]

subject to warp, block, allocation-granularity, shared-memory, and cluster limits. This is why “2,048 threads per SM” and “one 128-thread warpgroup issues WGMMA” are both true—and why optimized attention often reports low occupancy without spilling.

8.Limits and the final mental model

  • TMEM is datacenter-Blackwell-specific. The tcgen05 path described here targets SM100/SM100a, such as B200 and GB200. Consumer Blackwell SM120 does not expose this TMEM path.
  • TMEM is not general scratch space. CUDA ALU instructions cannot compute directly on it. Results must be loaded to registers for softmax, activation functions, conversion, or arbitrary elementwise work.
  • Low occupancy can remain. A Blackwell kernel may still use almost all available shared memory or many registers for its non-MMA stages. TMEM removes accumulator pressure; it does not make other resources infinite.
  • TMEM alone is not a benchmark result. FA4 combines TMEM with larger MMA tiles, different pipelining, staged P stores, two-CTA modes, and a redesigned softmax. Isolating the gain from one feature requires a controlled kernel comparison.
Mental model

Ampere: threads carry operands and results. Hopper: shared memory feeds an asynchronous 128-thread MMA, but threads still carry the result. Blackwell: one thread dispatches the MMA and the Tensor Core carries its own result in TMEM. NVIDIA added 256 KB per SM because the matrix engine had outgrown the register file as its long-lived accumulator store.
